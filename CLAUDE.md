# Working on Tributary

## Commits and pull requests

- **No attribution lines, anywhere.** No "Co-Authored-By: Claude", "Claude-Session:", "Generated with Claude Code", "Generated by Claude Code" or similar, in commit messages, pull request titles or descriptions, or comments. `.claude/settings.json` turns off the ones Claude Code adds by itself.
- **Always remove the "Generated by Claude Code" footer.** A pull request opened or edited from a Claude Code cloud session gets a `---` line and "_Generated by [Claude Code](…)_" added to the end of its description, and it comes back after every edit made from there. The **Tidy pull requests** workflow (`.github/workflows/tidy-pull-requests.yml`) removes it within a minute. After opening or editing a pull request, check that the footer is gone; if it isn't (the workflow didn't run), remove it from a session that can edit the description without it coming back, or ask the maintainer to.
- **Commits are the maintainer's.** Author and committer are the repository's owner, never Claude, and commits from a cloud session aren't signed with the session's key.
- **Branches:** make a branch from `develop` for each change and open a pull request into `develop`. `main` only changes through a pull request from `develop`. Releases are built from `main` (see `docs/development.md`).
- **Label every pull request into `develop`** with one of `fix`, `feature` or `breaking`: the label decides the next version (see `docs/development.md`), and the Labels check fails without one.
- **Every pull request is merged with a merge commit**, into `develop` and into `main`: never "Squash and merge" or "Rebase and merge", which copy the commits and leave the branch looking unmerged in the graph.
- **Rebase before merging:** before merging a pull request into `develop`, rebase its branch onto the latest `develop` and push it (`--force-with-lease`), so the branch starts from the tip of `develop` and the graph shows a short loop that joins straight back in. If its checks had passed and the rebase had no conflicts, merge it straight away, without waiting for them to run again: each merge into `develop` is checked again as merged. A pull request from `develop` into `main` isn't rebased.
- **Releases go through the checklist:** the pull request from `develop` into `main` has the release checklist (`.github/release-checklist.md`) as its description. Ready to release lists the boxes left unticked as reminders; they don't block the merge. Tick only what you've checked yourself, with a line under the item saying how. Tick the items on real computers (Windows, macOS, the desktop end-to-end tests) only when the maintainer says they've done them, and say so under them.

## Writing commit messages and pull request descriptions

Commits go out under the maintainer's name and are public, so they get quoted out of context. Write them as an experienced engineer would.

- **Only facts about the change.** Plain technical terms: what changed and why. No commentary or chatty asides, and nothing that sounds unsure. Write "CI: run the Rust checks when `generated.ts` changes", not "…and the guide says how it works".
- **Every sentence should read well quoted on its own.**
- **Mention side effects** (regenerated files, dependency bumps, changed defaults) in a final line or bullet.

### Commit messages

- **Subject:** imperative, specific, under 72 characters: "Remember the window's position between launches", not "Window improvements".
- **Body:** what changed and why, wrapped at 72 columns. Name the files, settings or behaviour that changed.

### Pull request descriptions

- **Start with the problem** in one or two sentences: what was wrong or missing, as a user or developer would see it.
- **Changes:** a short list of what the pull request does, naming files, settings and behaviour.
- **Tested:** what was run (checks, tests, the app itself) and the results, and what couldn't be tested, with the reason.
- Refer to design options by what they are, not only by a letter from a conversation ("the by-folder layout", not just "option 2").

## Release notes

- **Every new thing has a picture of it working.** Each item under **New** in `docs/release-notes/v<version>.md` has a short recording under it, on its own indented line: `![what it shows](v<version>/<name>.webp)`. Record it with `npm run preview:clips -- v<version>` from a scene in `tools/preview/clips/v<version>.mjs` (see `tools/preview/README.md`), on the demo repositories, so no real names show. Watch what it shows before committing it. `src/lib/whatsNew.test.ts` fails without one, or if one is over 400 KB.
